# 牛只智能监控平台开发阶段规划与验收标准

文档版本：`V1.0`  
文档日期：`2026-04-06`  
项目名称：`牛只智能监控平台`  
文档类型：`Development Roadmap & Acceptance Criteria`

## 1. 文档目的

本文档基于现有产品需求文档与系统架构设计文档，整理平台后续开发的阶段划分、交付物、验收标准、里程碑和风险控制要求，作为后续开发、联调、演示和答辩的执行依据。

本文档重点解决以下问题：

- 当前阶段先做什么、后做什么
- 每个阶段需要交付哪些内容
- 每个阶段如何判断是否完成
- 各阶段之间的依赖关系是什么
- 如何控制范围，避免开发失焦

## 2. 编写依据

本文档主要依据以下两份文档整理：

- `牛只智能监控平台_产品需求文档.md`
- `牛只智能监控平台_系统架构设计文档.md`

同时结合当前项目工作区现状进行调整：

- 当前 `code` 目录下主要为 `YOLOv8` 与 `KNN` 相关实验代码
- 平台前端、业务后端、推理服务、边缘代理等工程化目录尚未正式搭建
- 因此开发顺序必须优先完成平台底座与接口契约，而不是直接堆叠页面功能

## 3. 总体开发策略

### 3.1 开发原则

- 先完成 `P0` 范围，优先形成可演示、可迭代的业务闭环
- 先打基础工程，再接入算法能力，再补告警与分析能力
- 先做“结构化结果闭环”，再追求复杂实时视频能力
- 先做最小可用规则与告警，再逐步增强规则灵活性
- 对多租户、无人机、复杂控制等扩展能力仅做预留，不纳入首期主开发路径

### 3.2 总体目标

首期目标不是一次性做成完整商业产品，而是完成一个具备以下能力的平台可用版：

- 用户可登录系统
- 用户可管理设备与区域
- 系统可接入现有 `YOLOv8 + KNN` 识别结果
- 系统可将识别结果结构化保存为行为事件
- 系统可根据规则生成基础告警
- 用户可查询历史行为与告警记录
- 首页可展示关键监控信息
- 平台可接收边缘设备上报结果

### 3.3 范围控制

首期纳入开发的核心范围如下：

- 登录与基础权限管理
- 设备管理
- 区域标注
- 行为事件入库
- 基础告警中心
- 异常规则配置
- 历史查询与基础统计
- 首页监控总览
- 边缘上报接口

首期只预留、不重点展开的内容如下：

- 无人机接入
- 云台精细控制
- 复杂审批流
- 精细化个体身份识别
- 多种边缘硬件统一接入
- 完整 SaaS 多租户体系

## 4. 阶段划分总览

本项目建议划分为八个阶段：

1. 阶段 0：需求冻结与技术底稿
2. 阶段 1：项目骨架与基础环境
3. 阶段 2：认证、权限与主数据管理
4. 阶段 3：算法接入服务化与事件入库
5. 阶段 4：告警规则、告警中心与历史查询
6. 阶段 5：首页总览与监控详情页
7. 阶段 6：边缘设备上报与接口预留
8. 阶段 7：性能、安全与发布准备

阶段之间的总体依赖关系如下：

- 阶段 0 是整体范围与执行基线
- 阶段 1 是所有业务开发的工程基础
- 阶段 2 为后续所有页面与接口提供身份和数据边界
- 阶段 3 是行为事件、规则判断和历史分析的前提
- 阶段 4 构成平台核心业务闭环
- 阶段 5 负责形成完整可演示前端体验
- 阶段 6 负责兼容云端与边缘两类接入模式
- 阶段 7 负责将系统从“能跑”提升到“稳定可展示”

## 5. 各阶段详细规划

### 5.1 阶段 0：需求冻结与技术底稿

#### 阶段目标

在正式开发前，将需求范围、系统边界、页面清单、数据模型和接口范围统一下来，避免边开发边改方向。

#### 主要任务

- 明确 `P0`、`P1`、`P2` 范围
- 确认首期页面范围
- 确认首期核心模块范围
- 确认数据库核心实体
- 确认主要 REST API 与边缘上报接口范围
- 确认工程目录结构与模块职责

#### 交付物

- 开发阶段规划文档
- 页面清单
- 模块清单
- 核心实体清单
- 接口清单
- 技术栈清单
- 目录结构草案

#### 验收标准

- 已明确首期必须开发内容与明确延期内容
- 已输出统一模块划分，后续不再频繁调整模块边界
- 已确定首期核心实体至少包括：
  - `user`
  - `farm`
  - `device`
  - `zone`
  - `behavior_event`
  - `alert_rule`
  - `alert`
  - `edge_report`
- 已确定首期接口范围至少覆盖：
  - 登录
  - 当前用户
  - 设备管理
  - 区域管理
  - 行为事件查询
  - 告警查询与处理
  - 规则配置
  - 边缘心跳与结果上报
- 团队成员对首期开发边界理解一致

### 5.2 阶段 1：项目骨架与基础环境

#### 阶段目标

完成平台基础工程搭建，使前后端、数据库和开发环境可以独立启动、联调和迭代。

#### 主要任务

- 创建前端工程 `code/web`
- 创建后端工程 `code/api`
- 创建推理服务工程 `code/inference-service`
- 创建共享契约目录 `code/shared/contracts`
- 创建基础基础设施目录 `code/infra`
- 搭建本地开发环境与启动说明
- 配置基础 lint、格式化与测试工具

#### 交付物

- Vue 3 + TypeScript 前端初始化工程
- FastAPI 后端初始化工程
- Alembic 迁移框架
- Docker Compose 基础配置
- 环境变量模板
- README 启动文档
- 基础健康检查接口

#### 验收标准

- 前端项目可本地启动，并能访问基础页面
- 后端项目可本地启动，并能访问 `/health` 或等价健康检查接口
- PostgreSQL 可在本地开发环境中完成连接
- 数据库迁移命令可执行成功
- 前后端具备基础目录结构，不是单文件或脚本堆叠模式
- 提供一套清晰的本地启动步骤，新成员可按文档复现环境

### 5.3 阶段 2：认证、权限与主数据管理

#### 阶段目标

完成平台访问控制与基础业务主数据管理，建立系统最基本的可用能力。

#### 主要任务

- 实现用户登录
- 实现 Token 或 JWT 认证
- 实现当前用户信息接口
- 实现管理员与普通用户的基础权限隔离
- 实现农场、设备、区域相关表结构
- 实现设备管理 CRUD
- 实现区域标注 CRUD
- 实现基础审计埋点

#### 交付物

- 登录页
- 登录接口
- 当前用户接口
- 权限守卫
- 设备管理页
- 区域配置页
- 设备表、区域表、用户表等迁移脚本

#### 验收标准

- 未登录用户无法访问系统核心页面
- 登录成功后可正常访问首页与受保护页面
- 登录状态在刷新页面后可保持
- 退出登录后，用户状态和凭证被清除
- 管理员可新增、编辑、停用设备
- 普通用户只能查看授权范围内信息
- 用户可为指定设备新增、编辑、删除区域
- 区域名称、区域类型、区域坐标可持久化保存
- 设备与区域查询默认按农场或租户边界隔离

### 5.4 阶段 3：算法接入服务化与事件入库

#### 阶段目标

将现有 `YOLOv8 + KNN` 实验能力从脚本式调用转为平台可接入的服务能力，并打通行为事件入库链路。

#### 主要任务

- 抽取现有 `YOLOv8 + KNN` 处理逻辑
- 定义统一推理输入契约
- 定义统一推理输出契约
- 构建推理服务基础接口
- 将推理结果映射为 `behavior_event`
- 补充最小媒体资产元数据结构
- 支持图片、视频或设备来源的标准结果输入

#### 交付物

- 推理服务基础 API
- 推理输入输出数据结构文档
- `behavior_event` 表与相关迁移
- 结果写库逻辑
- 最小演示样例数据

#### 验收标准

- 推理服务可接收输入并返回结构化识别结果
- 统一输出字段至少包含：
  - 设备编号
  - 事件时间
  - 行为类型
  - 牛只数量
  - 置信度
  - 模型名称
  - 模型版本
  - 推理来源
- 后端可接收推理结果并写入 `behavior_event`
- 同一测试视频可重复导入并生成结构化记录
- 推理服务与业务后端解耦，业务后端不直接依赖实验脚本入口
- 更换模型实现时，业务后端不需要推倒重做接口层

### 5.5 阶段 4：告警规则、告警中心与历史查询

#### 阶段目标

完成平台的核心业务闭环，即“识别结果进入平台后，自动结构化、自动判断、自动生成告警，并支持用户查询与处理”。

#### 主要任务

- 设计 `alert_rule` 与 `alert` 数据表
- 实现基础预设规则
- 实现最小自定义规则能力
- 实现告警生成逻辑
- 实现告警查询、详情、处理状态更新
- 实现历史行为查询
- 实现历史告警查询
- 实现基础统计图表

#### 交付物

- 告警中心页
- 告警详情页
- 告警状态流转接口
- 规则配置页
- 历史分析页
- 规则执行服务
- 告警与事件查询接口

#### 验收标准

- 平台至少支持以下 3 类规则中的 3 类以上：
  - 持续卧躺超时
  - 长时间停留于指定区域
  - 设备离线
  - 视频流中断
  - 长时间未进入饮水区
- 告警可正常生成并保存到数据库
- 用户可查看告警列表与告警详情
- 用户可对告警更新处理状态
- 历史行为支持按时间范围、设备、行为类型分页筛选
- 历史告警支持按状态、等级、规则来源分页筛选
- 图表页面至少支持折线图、柱状图、占比图中的任意两类
- 行为事件数量、告警数量与统计图表结果一致

### 5.6 阶段 5：首页总览与监控详情页

#### 阶段目标

将后台能力转化为直观的业务界面，使平台进入“完整可演示、完整可讲解”的状态。

#### 主要任务

- 实现首页仪表盘
- 实现最近事件与最近告警展示
- 实现设备状态汇总展示
- 实现单设备监控详情页
- 将区域配置入口与设备详情整合
- 将行为事件与告警信息在设备详情中串联展示

#### 交付物

- 首页/监控总览页
- 监控详情页
- 设备状态卡片
- 最近事件列表
- 最近告警列表
- 跳转链路与导航结构

#### 验收标准

- 首页至少展示以下关键指标：
  - 在线设备数
  - 离线设备数
  - 当日行为事件数
  - 当前未处理告警数
- 首页可展示最近事件和最近告警
- 首页可从列表跳转到设备详情或告警详情
- 监控详情页可展示单设备最新行为识别结果
- 监控详情页可查看该设备的区域信息与最近告警
- 用户进入系统后三步以内可到达核心功能页面
- 首页展示结果与数据库统计口径保持一致

### 5.7 阶段 6：边缘设备上报与接口预留

#### 阶段目标

在平台具备云端推理能力的基础上，进一步支持 `Jetson Nano` 等边缘设备作为标准数据输入源接入。

#### 主要任务

- 设计边缘设备凭证机制
- 实现心跳上报接口
- 实现识别结果上报接口
- 实现截图或片段元数据上报接口
- 将边缘上报结果转换为事件与告警
- 实现边缘设备状态查看能力
- 实现最小上报日志留存能力

#### 交付物

- `edge_report` 表与迁移
- 设备凭证机制
- 心跳接口
- 结果上报接口
- 上报日志记录
- 设备最近上报时间展示

#### 验收标准

- 边缘设备可使用凭证完成身份认证
- 心跳接口可更新设备最近上报时间
- 识别结果上报后可成功保存原始记录
- 上报结果可转换为 `behavior_event`
- 满足规则条件时可进一步生成告警
- 平台可根据设备编号将边缘结果映射到正确设备
- 当设备长时间未上报时，平台能将其标记为异常或离线
- 云端推理与边缘上报两种模式可共存，不互相冲突

### 5.8 阶段 7：性能、安全与发布准备

#### 阶段目标

将平台从“功能已具备”提升到“稳定可演示、可答辩、可持续迭代”的状态。

#### 主要任务

- 为高频查询建立索引
- 优化首页统计查询
- 为列表接口增加分页与筛选
- 增加首页缓存或热点数据缓存
- 增加密码安全存储与基本安全控制
- 增加接口限流或最小防滥用能力
- 增加审计日志
- 增加健康检查
- 输出部署文档与演示文档

#### 交付物

- 索引优化脚本
- 首页缓存策略
- 安全加固实现
- 审计日志表或日志记录机制
- 部署文档
- 演示部署环境
- 答辩演示脚本

#### 验收标准

- 密码仅以安全哈希方式保存，不得明文存储
- 关键操作具备审计记录
- 登录接口具备最小安全控制能力
- 高频列表接口全部支持分页
- 行为事件、告警、边缘上报等高频查询字段已有索引
- 首页核心统计可在合理时间内完成加载
- API、数据库、推理服务具备健康检查能力
- 演示环境可从部署文档完成完整启动
- 可完成一次端到端演示：
  - 登录系统
  - 查看首页
  - 管理设备
  - 查看区域
  - 导入识别结果
  - 生成告警
  - 查询历史

## 8. 阶段验收组织建议

为避免阶段完成后才发现问题，建议每个阶段按以下方式做阶段验收：

- 文档验收：检查是否有对应说明、接口定义、表结构说明
- 功能验收：按页面和接口逐项演示
- 数据验收：检查数据库中是否有正确落库记录
- 联调验收：检查前后端与推理服务是否贯通
- 回归验收：检查新功能是否破坏已有链路

每阶段完成时建议至少整理以下内容：

- 已完成功能列表
- 未完成问题列表
- 已知缺陷列表
- 下阶段依赖事项

## 9. 风险与控制措施

### 9.1 算法效果与平台开发节奏脱节

风险说明：

- 若持续纠结模型精度，会拖慢平台开发进度

控制措施：

- 首期以“可接入、可展示、可结构化”为主
- 先固定一版可用模型，后续再逐步迭代精度

### 9.2 范围膨胀导致阶段失控

风险说明：

- 容易在开发过程中加入无人机、复杂权限、复杂实时流媒体等新目标

控制措施：

- 严格按 `P0` 开发
- `P1` 和 `P2` 仅预留结构，不纳入当前主线开发

### 9.3 实时视频能力过早复杂化

风险说明：

- 多路视频、低延迟播放、实时叠框会明显增加系统复杂度

控制措施：

- 首期重点做结构化事件和静态结果展示
- 实时视频只做最小展示能力，不提前深挖流媒体方案

### 9.4 边缘设备联调不稳定

风险说明：

- 真实 `Jetson Nano` 接入可能因网络、协议、环境差异导致调试成本升高

控制措施：

- 先开发“模拟上报客户端”
- 先跑通接口协议，再接真实边缘设备

### 9.5 历史数据增长导致性能问题

风险说明：

- 行为事件和告警数据增长后，查询可能明显变慢

控制措施：

- 从首期开始统一分页
- 提前规划高频字段索引
- 后续为首页统计增加缓存和预聚合

## 10. 结论

本开发阶段规划建议采用“先底座、再闭环、后增强”的策略推进：

- 第一优先级是完成平台基础工程与主数据能力
- 第二优先级是打通 `YOLOv8 + KNN -> 行为事件 -> 告警 -> 历史查询` 的核心链路
- 第三优先级是完善首页展示、边缘接入、安全和性能优化

按照本文档推进，可逐步形成：

- 可开发
- 可联调
- 可演示
- 可答辩
- 可继续扩展

的牛只智能监控平台实施路径。
